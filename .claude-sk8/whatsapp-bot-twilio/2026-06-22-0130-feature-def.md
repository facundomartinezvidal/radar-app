# Feature: WhatsApp Bot — Twilio variant (HU-26 → HU-29)
Date: 2026-06-22
Status: Defined (OpenSpec artifacts created; no implementation)
Feature Branch: `feat/whatsapp-bot-twilio` (off `feat/whatsapp-bot`)
Base Branch: `main`

## Business Context
**Problem**: The WhatsApp bot is built and deployed on Meta WhatsApp Cloud API
(`feat/whatsapp-bot`), but Meta test mode never delivers outbound messages to the
developer's Argentine number (Graph returns a message id; nothing arrives) until
business verification — impractical for the academic Entrega 4. Twilio's WhatsApp
Sandbox delivers to a real AR number after a `join <keyword>` opt-in, no verification.
**Target users**: same RADAR personas; immediate target is the demo/Entrega.
**Priority**: P1 — needed for a live WhatsApp demo.
**Success metric**: bot replies actually arrive on the AR test phone end-to-end.

## Scope — transport swap only
Provider-agnostic pieces from `feat/whatsapp-bot` are **reused unchanged**:
schema (4 tables), 9 RPCs, `types/supabase.ts`, intent classifier, Whisper transcribe,
capture→confirm state machine, queries, recommendations, `extract-document` /
`generate-insights` internal bypass, `profile/whatsapp.tsx`. Only the messaging adapter
changes.

| Seam | Meta (current) | Twilio (this branch) |
|---|---|---|
| Caller auth | GET `hub.challenge` + `X-Hub-Signature-256` (HMAC-SHA256 raw body) | `X-Twilio-Signature` (HMAC-SHA1 of URL + sorted params, base64); no GET handshake |
| Inbound | JSON `entry[].changes[].value.messages[]` | form-encoded `From`/`Body`/`NumMedia`/`MediaUrl{i}`/`MessageSid` |
| Idempotency key | Meta message `id` | Twilio `MessageSid` (same `provider_message_id` column) |
| Reply | Graph `POST /{phone_number_id}/messages` | Twilio Messages API (`Accounts/{sid}/Messages.json`, Basic auth) |
| Media fetch | media-`id`→URL→bytes (bearer) | single GET of `MediaUrl{i}` (Basic auth) |
| Number form | strip `+`; AR `549`→`15` transform | strip `whatsapp:` prefix; no transform (Twilio normalizes) |
| Secrets | `WHATSAPP_ACCESS_TOKEN`/`_PHONE_NUMBER_ID`/`_APP_SECRET`/`_VERIFY_TOKEN` | `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_WHATSAPP_FROM` |

## Locked decisions
- Provider: **Twilio WhatsApp Sandbox** (free; `join <keyword>` opt-in, 24h session window).
- Reply: keep ack-fast / reply-async (empty `<Response/>` 200, then Messages API).
- No new migration; reuse shipped tables + RPCs verbatim.
- Same function name `whatsapp-webhook`; one provider deployed at a time (branches mutually exclusive).

## Key edge cases (full set in specs)
Invalid `X-Twilio-Signature` → 403; duplicate `MessageSid` → 200 short-circuit; unlinked
number → link/help only; expired/reused/invalid/already-linked code; sandbox session
expired → user must `join` again; media fetch failure → resend prompt; ambiguous parse →
clarify; currency default ARS surfaced; zero/negative reject; Groq timeout; pending-confirm
expiry; duplicate confirm no double-write.
