# Feature: WhatsApp Bot (HU-26 → HU-29)
Date: 2026-06-21
Status: Approved
Feature Branch: `feat/whatsapp-bot`
Base Branch: main

## Business Context
**Problem Statement**: RADAR users manage money across wallets and want to register expenses / check balances without opening the app. WhatsApp is where Argentine young adults already live — the "WhatsApp conversational capture" pillar of the BMC.
**Target Users**: All three personas (estudiante, joven profesional, independiente multi-moneda).
**Success Metrics**: A linked user can register a valid expense from WhatsApp (text/audio/image/pdf) and see it in the app; can query totals and get recommendations — all via natural language.
**Priority**: MVP / Entrega 4 (HU-26/27 ALTO, HU-28/29 MEDIO).

### Locked decisions
| Decision | Choice |
|---|---|
| Provider | Meta WhatsApp Cloud API (free tier; test number ≤5 recipients until business verify) — *changed from Twilio after review* |
| Linking (HU-26) | App one-time code → user sends to bot → bind E.164 ↔ user |
| Interaction | Natural language via Groq LLM intent + entities |
| Build scope | End-to-end deployed against Cloud API test number with a real phone |

## Functional Requirements
- **HU-26**: Link/unlink a WhatsApp number to the Supabase account via one-time code.
- **HU-27**: Register expense/income from text, audio (Whisper), image & pdf (extract-document) — always with a confirmation step before write.
- **HU-28**: Query movements ("¿cuánto gasté este mes?", "¿en qué gasté?") via DEFINER read RPCs.
- **HU-29**: Recommendations ("¿cómo vengo?") via generate-insights.

## Critical Architecture
Webhook is called by Meta Cloud API with **no Supabase JWT** → cannot use INVOKER RPCs keyed on `auth.uid()`. Solution: single `whatsapp-webhook` edge fn (`verify_jwt=false`) — answers Meta's GET verify handshake, authenticated on POST by **`X-Hub-Signature-256` (HMAC-SHA256, app secret)**, resolves number→user_id, acts via **DEFINER `_for(p_user_id,…)` RPCs (Pattern 1, REVOKE from anon/public/authenticated)**. All privilege escalation confined to one trust boundary.

## Non-Functional
- No synchronous reply channel → ack 200 fast, handle + reply via Graph API `POST /{phone_number_id}/messages` inside `EdgeRuntime.waitUntil`. Media via media-id→URL→bytes (bearer token).
- Idempotency via `whatsapp_messages` UNIQUE on Meta message `id`.
- Secrets in edge env only: `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, optional `WHATSAPP_INTERNAL_SECRET`; `GROQ_API_KEY` exists.

## New Schema
`whatsapp_links`, `whatsapp_link_codes`, `whatsapp_messages`, `whatsapp_conversations` (all RLS, dual-shipped).

## New RPCs
`create_link_code` (INVOKER), `redeem_link_code`, `resolve_wa_user`, `import_transactions_for`, `get_personal_totals_for`, `get_expense_by_category_for`, `get_expense_by_period_for`, `get_income_by_period_for`, `unlink_wa` (DEFINER Pattern 1).

## Edge Cases
Unlinked number → link/help only; expired/reused/invalid code; already-linked (same vs other user); ambiguous parse → clarify; low OCR confidence → flag; multi-tx card statement → import-all confirm; media/audio fetch failure; invalid `X-Hub-Signature-256` → 403; GET verify token mismatch → 403; status-event ignore; duplicate webhook delivery → 200 short-circuit; concurrent messages (conversation-row lock); currency ambiguity (default ARS, surfaced in confirm); zero/negative amount reject; unknown language → Spanish help; pending-confirmation expiry; Groq timeout.
