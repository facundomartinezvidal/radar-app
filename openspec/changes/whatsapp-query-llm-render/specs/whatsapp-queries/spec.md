## ADDED Requirements

### Requirement: LLM-rendered query and chat replies

The system SHALL render expense/income totals queries, category queries, and chat replies as natural
rioplatense Spanish (voseo) generated by the LLM, with at most a few emojis for visual hierarchy and a
WhatsApp-friendly length (≈ 6 lines). `listMode` row-lists SHALL remain fully deterministic (no LLM).

#### Scenario: Totals query rendered by LLM
- **WHEN** a linked user asks "¿cuánto gasté este mes?" and Groq responds successfully
- **THEN** the reply is a natural-language LLM message containing the period's expense totals, with
  moderate emoji use, instead of the bare deterministic template

#### Scenario: Chat reply rendered by LLM
- **WHEN** a linked user asks a conversational finance question and Groq responds successfully
- **THEN** the reply is the LLM's natural-language answer over the user's financial context

#### Scenario: List mode stays deterministic
- **WHEN** a linked user asks "mis últimos 5 gastos" (listMode)
- **THEN** the reply is the deterministic movement list with no LLM call

### Requirement: Figures are computed deterministically and copied verbatim

The system SHALL compute all monetary amounts, counts, dates, and percentages deterministically via
RPCs and pre-format them into a context block; the LLM SHALL only frame those exact strings in prose.
The system MUST NOT allow the LLM to compute or invent any figure.

#### Scenario: Every reply figure exists in the context block
- **WHEN** the LLM returns a rendered reply
- **THEN** every monetary token (e.g. "$ 45.000,00", "USD 100,00") and percentage in the reply
  appears verbatim in the deterministic context block

#### Scenario: Fabricated figure is rejected
- **WHEN** the LLM output contains a monetary or percentage token that is NOT present in the context
  block
- **THEN** the system discards the LLM output and sends the deterministic fallback instead, and logs
  the rejection

### Requirement: Deterministic fallback on LLM failure

Because the LLM is in the critical path of every rendered query, the system SHALL fall back to the
existing deterministic template reply whenever the Groq call fails for any reason, and the handler
SHALL never throw a user-visible error.

#### Scenario: Groq times out
- **WHEN** the Groq render call exceeds its 8-second timeout
- **THEN** the user receives the deterministic template reply for that query

#### Scenario: Groq API key missing
- **WHEN** `GROQ_API_KEY` is not configured
- **THEN** the user receives the deterministic template reply with no error surfaced

#### Scenario: LLM output too long
- **WHEN** the LLM output exceeds the WhatsApp-safe length cap
- **THEN** the system truncates at a sentence boundary or falls back to the deterministic reply

### Requirement: Complete query coverage

The system SHALL answer queries about expense totals, income totals, net balance, expense-by-category,
income-by-category, recent movements, and month-over-month comparison, each scoped to the resolved
period.

#### Scenario: Income totals query
- **WHEN** a linked user asks "¿cuánto cobré este mes?"
- **THEN** the reply reports income totals per currency for the period using `get_income_totals_for`

#### Scenario: Net balance query
- **WHEN** a linked user asks "¿cómo viene mi balance?"
- **THEN** the reply reports net balance per currency, computed deterministically as incomes minus
  expenses, with the correct sign

#### Scenario: Income-by-category query
- **WHEN** a linked user asks about their income sources by category
- **THEN** the reply reports income grouped by category for the period using
  `get_income_by_category_for`

#### Scenario: Month-over-month comparison
- **WHEN** a totals query is rendered
- **THEN** the context block includes the prior-period expense total and the deterministically
  computed percentage change, available for the LLM to mention

### Requirement: Period-aware chat

The chat handler SHALL resolve the period requested by the user (today, week, month, prev_month, year,
or a custom range) rather than always using the current month.

#### Scenario: Chat about a past period
- **WHEN** a linked user asks "¿en qué se me fue la plata la semana pasada?"
- **THEN** the assembled context covers last week's data, not the current month

### Requirement: Income aggregation RPCs

The system SHALL provide `get_income_totals_for(p_user_id, p_from, p_to)` returning
(currency, total, count) and `get_income_by_category_for(p_user_id, p_currency, p_from, p_to)`
returning (category_id, category_name, color, icon, total, count). Both SHALL be SECURITY DEFINER with
EXECUTE revoked from anon/public/authenticated and granted only to service_role. Incomes have no group
splits, so totals are a plain sum.

#### Scenario: Income totals grouped per currency
- **WHEN** `get_income_totals_for` is called for a user with ARS and USD incomes in the period
- **THEN** it returns one row per currency with the summed total and count

#### Scenario: Income totals empty period
- **WHEN** `get_income_totals_for` is called for a period with no incomes
- **THEN** it returns no rows

#### Scenario: RPC not callable by authenticated role
- **WHEN** an authenticated (non-service-role) caller attempts to execute either RPC
- **THEN** execution is denied
