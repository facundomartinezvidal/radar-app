# ADR: Custom categories — schema and write strategy

**Date:** 2026-06-07
**Status:** Accepted
**Scope:** `radar-app` — HU-16 (categorías personalizadas)

---

## Context

RADAR ships with 9 system categories seeded at DB level. HU-16 adds per-user
custom categories so users can classify expenses that don't fit the default
taxonomy. The system categories must remain globally readable; custom categories
must be visible and mutable only by their owner.

Open choices at the start of this feature:

1. **Storage shape** — extend `categories` vs a separate `user_categories` table.
2. **Slug uniqueness** — global unique vs scoped uniqueness per owner.
3. **Write path** — RPC vs direct single-table CRUD under RLS.
4. **Delete impact** — cascade delete expenses vs set null.
5. **OCR integration** — static category list in prompt vs dynamic, and what
   to return when no category matches.

---

## Decision

### 1. Extend `categories` with nullable `user_id` (not a separate table)

A single `categories` table with a nullable `user_id` column:

- `user_id IS NULL` = system category — readable by all authenticated users,
  mutable only by service_role (seeding / migrations).
- `user_id = auth.uid()` = user-owned category — full CRUD under RLS.

A separate `user_categories` table was considered for a cleaner separation of
system and custom data. Rejected because:

- Every consumer of categories (`listCategories`, `CategoryPicker`, OCR mapping)
  would need a UNION or a JOIN, adding query complexity with no offsetting benefit.
- The `expenses.category_id` FK would need to reference both tables or a view.
- The distinction is already encoded in a nullable column; a separate table
  duplicates the same information with more surface area.

### 2. Two partial unique indexes replace the global slug unique

The original `UNIQUE(slug)` constraint prevented two users from creating
categories with the same name (same slug). Replaced by:

- `categories_slug_system_unique`: `(slug) WHERE user_id IS NULL` — one system
  slug globally.
- `categories_slug_user_unique`: `(user_id, slug) WHERE user_id IS NOT NULL` —
  one slug per user, also enforcing no duplicate names per user.

This allows user A and user B to each have "Farmacia" without conflict, while
system slugs remain globally unique and per-user slugs remain unique within the
user's own set.

The slug is generated by the repository (`normalizeName(name)`) — the client
never supplies it directly.

### 3. No RPC — direct single-table CRUD under RLS

HU-18 (line items) required transactional RPCs because a single user action
touches two tables atomically (`expenses` + `expense_items`). Custom categories
are a single-table write: one INSERT, UPDATE, or DELETE on `categories`. RLS
is sufficient; no stored procedure adds value here.

The repository's `createCategory`, `updateCategory`, and `deleteCategory`
call Supabase client methods directly. The Postgres 23505 unique-violation
error is caught and mapped to the user-facing message
"Ya tenés una categoría con ese nombre."

### 4. Delete = `on delete set null` on `expenses.category_id`

When a user deletes a custom category, linked expenses lose their category
(`category_id → null`) rather than being deleted. This preserves financial
history — amount, date, description, and line items remain intact.

`on delete cascade` was considered and rejected: silently deleting an expense
because the user renamed a taxonomy entry would be a destructive and
surprising action, violating RADAR's core "trazabilidad" (traceability) value.

The FK constraint `expenses.category_id references categories(id) on delete set null`
was already in place from the initial schema. HU-16 does not change it.

### 5. OCR: dynamic category list + `suggestedNewCategory`

The `extract-receipt` edge function (v3) accepts an optional `categories: string[]`
parameter. When present, the function builds the category selection prompt
dynamically, instructing the model to choose from the user's actual taxonomy
(system + custom combined). When no category in the list fits the receipt, the
function returns `suggestedNewCategory` — a short Spanish name (≤40 chars,
trimmed) derived from the receipt content.

Key design choices:

- **No silent auto-creation.** The suggested name is surfaced to the user as a
  "Crear categoría '<nombre>'" CTA on the review screen. The user confirms before
  the category is created. This prevents the taxonomy from growing with AI noise.
- **Match wins over suggestion.** `mapOcrToPrefill()` only sets
  `suggestedCategoryName` when `category_id === null`. If the model found a
  match, the suggestion is discarded.
- **Backward compat.** If the `categories` param is absent or empty (old client,
  first load before cache is warm), the edge function falls back to the 9 system
  category names. No breaking change.
- **Truncation in edge function.** The function truncates `suggestedNewCategory`
  to ≤40 chars before returning it; the client schema validates again.

---

## Alternatives considered

### A. Separate `user_categories` table

A dedicated table for custom categories with a separate FK on `expenses`. Rejected
because it forces UNION queries at every call site and splits what is logically
one taxonomy entity across two tables. The nullable `user_id` pattern is simpler
and consistent with how the DB already distinguishes ownership on other tables.

### B. Keep global slug unique, add owner column

Retaining `UNIQUE(slug)` would mean user A creating "Farmacia" blocks user B
from doing the same. This is unreasonable for a personal taxonomy feature.
Partial unique indexes are the correct SQL primitive for scoped uniqueness.

### C. RPC for category CRUD

A stored procedure wrapping the INSERT/UPDATE/DELETE would add a network round
trip benefit only if multiple tables were involved. With a single-table write,
the extra abstraction layer is pure overhead.

### D. Auto-create category on OCR suggestion

The OCR model could silently create a new category when no existing one matches.
Rejected because: (1) auto-growing taxonomies lead to duplicates and noise;
(2) model hallucinations would create unwanted entries; (3) the user's
permission to modify their own taxonomy should require an explicit action.
Manual confirm with a pre-filled form is the correct UX.

### E. Cascade delete expenses on category delete

Deleting a category and all its linked expenses would be catastrophic for a
user who had hundreds of "Farmacia" purchases before deciding to rename the
category. `on delete set null` preserves the financial record while removing
the category label, which matches user expectations.

---

## Consequences

**Benefits:**

- Single `listCategories` query returns system + custom rows in one call;
  no UNION, no JOIN.
- Partial unique indexes enforce both the no-duplicate-slug-globally (system)
  and no-duplicate-name-per-user (custom) constraints at the DB level, with no
  application-side check needed.
- Direct CRUD under RLS is simpler to reason about and test than an RPC path.
- `on delete set null` preserves expense history — no user data is silently lost.
- OCR suggestion flow surfaces useful taxonomy hints without polluting the
  user's category list with AI noise.

**Tradeoffs:**

- `user_id IS NULL` as the system-category sentinel is an implicit convention;
  any future code that inserts into `categories` must be aware of it.
- The slug is stable between creates but can change on rename (slug is derived
  from name). Do not use slug as a stable external reference.
- `suggestedNewCategory` is a best-effort AI output — it can be empty, misspelled,
  or in the wrong language. Edge fn truncates; client validates; user confirms.

## Implementation

1. `supabase/migrations/20260607224119_custom_categories.sql` — alter `categories`:
   add `user_id` + `updated_at`, drop old slug unique, create two partial unique
   indexes + `user_id` index, add `categories_name_nonempty` check, replace
   `categories_select_authenticated` with 4 ownership-aware RLS policies, add
   `categories_set_updated_at` trigger.
2. `lib/category-options.ts` — `CATEGORY_ICONS` (curated Lucide names) and
   `CATEGORY_COLORS` (DS palette hex values).
3. `lib/schemas/category.ts` — `createCategorySchema` + `updateCategorySchema`
   (name 1–40, icon/color enums).
4. `lib/repositories/categories.ts` — `listCategories`, `createCategory`,
   `updateCategory`, `deleteCategory`; `normalizeName` slug generation;
   23505 → friendly message.
5. `hooks/use-categories.ts` — TanStack Query mutations invalidating
   `categoryKeys.all` + `expenseKeys.all`.
6. `components/categories/category-form.tsx` — icon picker + color picker +
   live preview chip.
7. `components/categories/category-create-sheet.tsx` — bottom sheet wrapping
   the form.
8. `components/expenses/category-picker.tsx` — add "+ Categoría" chip; open
   sheet on tap; auto-select on create.
9. `app/(protected)/profile/categories.tsx` + `category-form.tsx` — Perfil
   CRUD screens.
10. `supabase/functions/extract-receipt/index.ts` (v3) — accept `categories[]`,
    dynamic prompt, `suggestedNewCategory`.
11. `lib/ocr.ts` — `extractReceipt` forwards category names;
    `mapOcrToPrefill` sets `suggestedCategoryName` when `category_id null`.
12. `app/(protected)/expense/review.tsx` — render suggestion CTA; open
    `CategoryCreateSheet`; assign `category_id` on confirm.
