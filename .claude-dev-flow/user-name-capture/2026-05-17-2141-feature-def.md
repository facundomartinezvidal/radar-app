**Date:** 2026-05-17
**Status:** Approved
**Feature Branch:** `feat/user-name-capture`
**Base Branch:** auto-detected at `/build` time (likely `main`)

## Business Context

**Problem Statement.** Hoy el signup pide email + password únicamente. La home muestra "Hola, {emailPrefix}" y un avatar con la primera letra del email — un placeholder que rompe la promesa del Design System ("avatares = iniciales sobre círculo con color por hash del nombre"). El producto carece de identidad real del usuario: no podemos saludarlo con su nombre, no podemos atribuir gastos en grupos, no podemos personalizar emails u OTPs.

**Target Users.** Todas las personas que se registran en RADAR (3 personas: el estudiante, el joven profesional, el independiente multi-moneda) + todas las cuentas existentes que se autenticaron antes de este feature.

**Success Metrics.**
- 100% de nuevos signups completan first_name + last_name (es requerido)
- 100% de usuarios existentes que abren la app completan profile-setup en su próxima sesión
- Home siempre muestra "Hola, {first_name}" (sin fallback a email prefix)
- Avatar siempre con 2 letras + color hash consistente

**Priority.** P0 — bloquea la pantalla Perfil, grupos compartidos (HU futura), y atribución en gastos.

## Decisiones de diseño (cerradas con el usuario)

| Decisión | Valor |
|---|---|
| Cuándo capturar | En signup form (2 inputs nuevos antes del email) |
| Storage | `auth.users.raw_user_meta_data.first_name/last_name` + sync trigger a `profiles.first_name/last_name` |
| Validación | Ambos requeridos, 2–40 chars, regex `/^[A-Za-zÀ-ÿñÑ\s'-]+$/`, trim |
| `display_name` | Computado por trigger: `first_name \|\| ' ' \|\| last_name` |
| Avatar fallback | 2 letras (FM) + color de fondo por hash del nombre completo (paleta 8-hue del DS) |
| Backfill usuarios existentes | Gate de onboarding: si `profiles.first_name = ''` y user autenticado → redirect a `/(auth)/profile-setup` antes de entrar a `(tabs)` |
| Usos adicionales | Pantalla Perfil/Settings, email templates OTP, hook listo para push + groups |

## Functional Requirements

### Happy Path

1. Usuario abre app → tap "Crear cuenta"
2. Sign-up form: ingresa **nombre**, **apellido**, email, password, confirm password
3. Submit → `supabase.auth.signUp({ email, password, options: { data: { first_name, last_name } } })`
4. Email OTP llega con "Hola {first_name}"
5. Usuario tipea código OTP en verify-otp screen
6. Trigger `handle_new_user` crea `profiles` con first_name, last_name, display_name
7. Redirect a `(tabs)/` → home muestra "Hola, Facundo" + avatar `FM` con color hash

### Error Paths

| Caso | Comportamiento |
|---|---|
| Nombre vacío | Zod: "Ingresá tu nombre." |
| Nombre con número/emoji | Zod: "Solo letras, espacios, guiones o apóstrofes." |
| Nombre <2 chars | Zod: "Mínimo 2 caracteres." |
| Nombre >40 chars | Zod: "Máximo 40 caracteres." |
| Apellido equivalentes | Mismos mensajes para campo apellido |
| signUp falla red | Mensaje genérico "No pudimos crear la cuenta. Probá de nuevo." |
| Email ya registrado | "Ya hay una cuenta con ese email." (existente) |

### State Model (user identity)

```
[no session]
  └── signUp(email, password, {first_name, last_name})
        └── auth.users insert
              ├── trigger handle_new_user → profiles insert (first_name, last_name, display_name)
              └── email OTP sent
[session pending OTP]
  └── verifyOtp(code)
        └── [session active, first_name present] → (tabs)/
[session active, first_name = '']  ← caso usuario legacy
  └── (protected)/_layout redirect → (auth)/profile-setup
        └── updateUser({ first_name, last_name })
              └── trigger handle_user_metadata_update → profiles update
                    └── auth listener USER_UPDATED → store rehidrata → gate deja pasar → (tabs)/
```

## Non-Functional Requirements

### Performance
- Sign-up sin extra round-trip vs. hoy (los nombres viajan en `options.data`)
- Avatar render: `useMemo` por `firstName + lastName` evita recompute de hash en cada render

### Security
- Nombre = PII. `profiles` ya tiene RLS `auth.uid() = id` (existente, no requiere cambios)
- `user_metadata` solo legible por su dueño (Supabase enforza)
- No logging de nombres en producción (Sentry breadcrumbs filtran ya)

### Reliability
- Trigger atómico con el insert en `auth.users` (mismo statement)
- Si trigger falla, signUp falla (constraint: profiles no puede quedar huérfano)
- USER_UPDATED event resync automático tras `updateUser`

### Scalability
- Cero impacto. Solo agrega 2 columnas text al `profiles`.

## Edge Cases

### Datos
- Trim solo espacios ("   ") → zod rechaza (post-transform `.min(2)`)
- Caracteres no permitidos (emoji, número, símbolo raro) → regex rechaza
- Caracteres permitidos (ñ, ç, ü, á, espacio, ', -) → aceptados
- Apellido compuesto ("Del Río"), con apóstrofe ("O'Brien"), con guión ("Martinez-Vidal") → aceptados
- Nombre muy largo (>40) → rechazado con mensaje claro

### Estado / sync
- `auth.users` existe pero no `profiles` → trigger update upsert (handle legacy)
- `updateUser` falla por red → form muestra error, no avanza
- JWT viejo con first_name='' justo después de updateUser → onAuthStateChange USER_UPDATED event re-hidrata store
- Usuario corta app entre signUp y verify-otp → próximo login va a OTP o profile-setup según estado

### UI / UX
- Email prefix muy corto ("a@x.com") → ya no se usa, gate fuerza nombre real
- Hash color colisiona entre usuarios → es OK (8 hues, no es identidad)
- Acento en mayúscula (Á) → `.toUpperCase()` funciona

### Seguridad
- PII en `profiles` → RLS existente (sin cambios)
- `user_metadata` solo legible por dueño → Supabase enforza

### Performance
- Avatar memo por firstName+lastName
- Trigger update solo procesa si `OLD.raw_user_meta_data IS DISTINCT FROM NEW.raw_user_meta_data`
