## Business Context

**Problem Statement**: Hoy un gasto escaneado guarda sólo el total. El usuario no sabe en qué se compone su compra (qué items, a qué precio). HU-18 (MVP, complejidad MEDIO, Entrega 3) agrega el detalle de renglones del ticket.

**Target Users**: Las 3 personas RADAR — estudiante, joven profesional, independiente multi-moneda. Caso primario: ticket de supermercado argentino con muchos renglones.

**Success Metrics**:
- OCR devuelve items en tickets con detalle legible
- Usuario puede corregir/agregar/borrar items antes de guardar
- Items persisten y se muestran en el detalle del gasto
- Pillar 1 (personal tracking) + base para pillar 3 (AI insights por item, roadmap)

**Priority**: P1 — MVP de Entrega 3, alimenta entrega 2026-06-01 ya pasada → siguiente release.

## Decisiones de entrevista (usuario, 2026-06-03)

| Decisión | Resolución |

## Functional Requirements

### User Story
Como usuario que escanea un ticket, quiero ver y editar el detalle de items (nombre, cantidad, precio unitario, total de línea) para saber exactamente en qué se compone mi gasto.

### Happy Path
1. Usuario escanea ticket → `extract-receipt` devuelve `{ ...campos actuales, items: [{name, quantity, unitPrice, lineTotal}] }`
2. Review screen muestra `ExpenseForm` con sección "Detalle" pre-llenada (colapsable, auto-expandida si hay items)
3. Usuario edita/agrega/borra items; qty×unit_price recalcula line_total; edición manual de line_total gana
4. Si `|Σ line_total − amount| > 0.5` → aviso amber no bloqueante
5. Submit → RPC `create_expense_with_items` (transaccional) → expense + items persisten
6. Detalle `[id].tsx` hidrata items vía select anidado; edición usa RPC `update_expense_with_items` (delete-all + reinsert)

### Error Paths
- OCR sin items / payload off-spec → `items: []` (zod `.catch([])`), form vacío editable
- Item sin nombre → drop silencioso en normalización
- Falla parcial insert → transacción RPC revierte todo (no hay gasto sin items huérfano)
- > 50 items → cap en edge function y en zod (`Máximo 50 ítems.`)

## Design Decisions (técnicas)

1. **Tabla `expense_items` separada** (no JSONB): constraints DB, queryable, habilita AI insights por item. `user_id` denormalizado → RLS patrón existente `(select auth.uid()) = user_id`, sin subquery join por fila.
2. **`line_total` requerido almacenado** (no generado): tickets argentinos imprimen total de línea; `unit_price` a menudo ausente; redondeos por peso hacen qty×price ≠ total legítimo. `quantity` default 1.
3. **Escritura atómica vía RPC** `security invoker` + `set search_path = ''`: un round-trip, transaccional.
4. **Update = delete-all + reinsert** en transacción. Limitación conocida: ids de items rotan en cada save. Revisar si futuro HU necesita identidad estable por item.
5. **Lectura**: select anidado `'*, category:categories(*), items:expense_items(*)'`, sort client-side por `position`.

## Schema (DDL exacto)

Ver plan aprobado en `/Users/fmartinezvidal/.claude/plans/lively-conjuring-wadler.md` — resumen:

```sql
create table public.expense_items (
  id uuid primary key default gen_random_uuid(),
  expense_id uuid not null references public.expenses (id) on delete cascade,
  user_id uuid not null references auth.users (id) on delete cascade,
  name text not null,
  quantity numeric(14,3) not null default 1 check (quantity > 0),
  unit_price numeric(14,2) check (unit_price >= 0),
  line_total numeric(14,2) not null check (line_total >= 0),
  position integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint expense_items_name_nonempty check (char_length(btrim(name)) between 1 and 120)
);
-- índices: (expense_id), (user_id) · RLS owner-only 4 policies · RPCs create/update_expense_with_items
```

`supabase/migrations/` nuevo en repo: baseline `20260517025226_init_profiles_categories_expenses.sql` + `20260518005107_add_first_last_name_to_profiles.sql` (reconstruidas por introspección, NO re-aplicar) + 2 nuevas (`create_expense_items`, `expense_items_rpc`) aplicadas vía MCP `apply_migration` con mismo nombre.

## Non-Functional Requirements

- **Performance**: OCR cap 50 items mantiene respuesta dentro del timeout 20s existente. Select anidado = 1 query.
- **Security**: RLS owner-only idéntica a `expenses`; RPC `security invoker` (corre bajo RLS del caller); `search_path = ''`.
- **Reliability**: escritura transaccional; zod defensivo `.catch()` en parsing OCR; backward compat (`items` ausente → `[]`).
- **Copy**: español rioplatense formal, sin emoji, tabular-nums en montos, Lucide icons (Plus, X, ChevronDown/Right).

## Out of Scope (explícito)

- Categoría por item (gasto mantiene categoría única)
- Analytics/insights por item (roadmap pillar 3)
- Búsqueda/filtrado por nombre de item en historial
- Identidad estable de item entre saves (ids rotan en update)
- Split de items entre miembros de grupo (espera tablas groups/splits)
- FX por item
